# Windows (win-x64, win-arm64) WGSL/WebGPU build and oracles

Copyright (c) 2026 Jeremy Ellis and contributors

This recipe produces the Windows product binaries: the pinned Cycles revision
with the CodeBrix WGSL/WebGPU device and the CPU device, behind the same native C
API and managed API as every other RID. Both Windows RIDs are built on an x64
Windows machine; win-arm64 is cross-compiled there and its payload is committed,
so an ARM64 Windows device only runs the tests. The test procedure is
[docs/TESTING-WINDOWS-X64.md](../../docs/TESTING-WINDOWS-X64.md).

## Decisions

- **One host per architecture, two WebGPU backends.** The shipped
  `CodeBrix.WebGpu.Native.MitLicenseForever` 1.0.290.1433 `codebrix_wgpu.dll`
  (win-x64 and win-arm64) contains wgpu's Direct3D 12, Vulkan and GL backends;
  the backend is chosen when the WebGPU instance is created
  (`native/src/webgpu_device.cpp`). Direct3D 12 is the default: it is part of
  Windows 10 and 11 and every GPU vendor's driver supports it, including GPUs
  with no native Vulkan driver (the Qualcomm Adreno GPUs of Windows on ARM
  devices, where Vulkan exists only through an optional compatibility pack).
  Vulkan is an explicit opt-in, `CODEBRIX_CYCLES_WEBGPU_BACKEND=vulkan`, used for
  diagnostics and for comparison with Linux (the same WGSL to SPIR-V path). A
  backend never falls back to another one, and never to the CPU.
- **DXC, not FXC.** Direct3D 12 compiles the WGSL kernels' HLSL with Microsoft's
  DirectX Shader Compiler. FXC (`d3dcompiler_47.dll`, part of Windows) failed to
  compile real Cycles kernels and was tens of times slower where it succeeded
  (measurements: `third_party/dxc-import.json`). The pinned, unchanged,
  Microsoft-signed `dxcompiler.dll` 1.9.2609.5 (University of Illinois/NCSA
  license) is a reviewed payload file in `native/binaries/<rid>/runtime/` beside
  its license text; it ships beside the host library, where the device finds it
  (`CODEBRIX_CYCLES_DXC_PATH` overrides the location). `dxil.dll` is not needed
  (DXC 1.8.2505 and later validate internally) and is not imported.
- **clang-cl from Visual Studio.** The toolchain is Visual Studio 2022 or later
  with its MSVC tools, Windows SDK and bundled LLVM (clang-cl, lld-link,
  llvm-lib), and Visual Studio's own CMake and Ninja
  (`tools/windows_toolchain.py`). It produces MSVC-ABI DLLs, accepts Clang's
  arithmetic options (the fixed-baseline CPU oracle) and is a Clang for the AST
  translation. Every other compiler distribution (Strawberry Perl, LLVM-MinGW,
  MSYS2, Cygwin, Git's Unix tools) is removed from the build environment and
  rejected in configured caches, compile commands and the compiler's dependency
  log, as the macOS recipes do for Homebrew.
- **Hybrid C runtime; no redistributable.** Every DLL links the C++ runtime
  statically and the Universal CRT (`ucrtbase.dll`, part of Windows 10 and 11)
  dynamically (`/MT` with `/NODEFAULTLIB:libucrt.lib ucrt.lib`), as .NET's own
  runtime does. No Visual C++ Redistributable is needed, and all DLLs share the
  Universal CRT's heap, so memory crosses DLL boundaries safely. The recipes
  reject any DLL that imports a Visual C++ runtime DLL.
- **Fixed-baseline CPU oracle.** As on Linux and macOS: Cycles' SSE4.2 kernels
  only on x64 (no AVX2/FMA kernel, never a native-architecture flag), the ARMv8-A
  base level on ARM64, no floating-point contraction and no reciprocal math.
  clang-cl ignores GCC-style math options with only a warning, and Cycles passes
  its own as `/clang:-ffp-contract=on /clang:-freciprocal-math`; the shared
  injection (`native/tools/inject_cycles.cmake`) and `native/host/targets.cmake`
  switch them off again in the same `/clang:` form, and the recipe checks the
  CPU kernel's compile line (last contraction and reciprocal options off, static
  runtime, SSE4.2 and no AVX/FMA on x64).
- **No image files.** As on macOS: OIIO's format plugins are all disabled,
  libpng is not built, `CBC_HOST_NO_IMAGE_FILES` is set, and the host rejects
  texture `filename` sockets with `CBC_UNSUPPORTED`. Callers pass decoded pixels;
  read and write image files with CodeBrix.Imaging, which the package does not
  depend on.
- **The same kernels as Linux.** The WGSL overlay is generated by the shared
  generators; on Windows the AST translation runs clang++ from Visual Studio.
  The generated `translated.wgsl` is byte-identical to the Linux copies retained
  in `native/evidence/*/generated/translated.wgsl`. Generated files are written
  with `\n` line endings (the recipe makes `Path.write_text` keep them), so the
  overlay bytes match Linux.
- **The pinned sources are unchanged.** A few Windows-only build helpers that
  the reviewed source profile excludes are replaced by independent files in
  `tools/dependencies/windows/` (zstd's and expat's version resource scripts,
  robin-map's debugger visualizer), placed into the recipe's work copy of the
  snapshot and recorded in the prefix provenance. Boost's in-repository build
  adapter defines the `BOOST_<LIB>_SOURCE`, `BOOST_ALL_DYN_LINK` and
  `BOOST_ALL_NO_LIB` macros that Windows DLLs need (`if(WIN32)` only).
- Reviewed deliverables go to `native/binaries/<rid>/` (runtime, unstripped and
  symbols) with provenance. The maintainer makes every commit and push.

the host build: `host/build/bin/` holds the host DLL, the consumers and gates,
the dependency DLLs, `codebrix_wgpu.dll` and `dxcompiler.dll` side by side.

## Build

From the repository root, in PowerShell or a Command Prompt (Git Bash rewrites
`/flag` arguments into paths):

```
python -I -X utf8 tools/dependencies/build_windows.py --rid win-x64 --jobs 16
python -I -X utf8 native/tools/build_cycles_windows.py --rid win-x64 --jobs 16
python -I -X utf8 tools/dependencies/build_windows.py --rid win-arm64 --jobs 16
python -I -X utf8 native/tools/build_cycles_windows.py --rid win-arm64 --jobs 16
```

`python -I -X utf8` is required: the recipes read every text file as UTF-8, as
on Linux and macOS, and `-I` ignores `PYTHONUTF8`. Each recipe records its
inputs (`provenance.json`, `invocation.json`) and `status.json`.

## Process exit with live hosts

`ABI.md` promises that a process may exit while hosts are alive. On Windows a
DLL's own `atexit` functions run at `DLL_PROCESS_DETACH`, after `ExitProcess`
has terminated every other thread, so closing the hosts there crashed
(`0xC0000409`, found by the host gate's `cpu-exit` step). The host registers its
exit hook in the process-wide table instead (`_crt_atexit`, which `exit()` runs
while all threads exist) and pins its DLL so the hook can never outlive it
(`native/host/cycles_host.cpp`); Linux and macOS keep `std::atexit`.
