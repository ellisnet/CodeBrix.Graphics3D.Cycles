# Windows (win-x64, win-arm64) WGSL/WebGPU build and oracles

Copyright (c) 2026 Jeremy Ellis and contributors

This recipe produces the Windows product binaries: the pinned Cycles revision
with the CodeBrix WGSL/WebGPU device and the CPU device, behind the same native C
API and managed API as every other RID. Both Windows RIDs are built on an x64
Windows machine; win-arm64 is cross-compiled there and its payload is committed,
so an ARM64 Windows device only runs the tests. The test procedure is
[docs/TESTING-WINDOWS-X64.md](../../docs/TESTING-WINDOWS-X64.md).

## Decisions

- **One host per architecture, two WebGPU backends.** The shipped
  `CodeBrix.WebGpu.Native.MitLicenseForever` 1.0.300.210 `codebrix_wgpu.dll`
  (win-x64 and win-arm64) contains wgpu's Direct3D 12, Vulkan and GL backends;
  the backend is chosen when the WebGPU instance is created
  (`native/src/webgpu_device.cpp`). Direct3D 12 is the default: it is part of
  Windows 10 and 11 and every GPU vendor's driver supports it, including GPUs
  with no native Vulkan driver (the Qualcomm Adreno GPUs of Windows on ARM
  devices, where Vulkan exists only through an optional compatibility pack).
  Vulkan is an explicit opt-in, `CODEBRIX_CYCLES_WEBGPU_BACKEND=vulkan`, used for
  diagnostics and for comparison with Linux (the same WGSL to SPIR-V path). A
  backend never falls back to another one, and never to the CPU.
- **DXC, not FXC.** Direct3D 12 compiles the WGSL kernels' HLSL with Microsoft's
  DirectX Shader Compiler. FXC (`d3dcompiler_47.dll`, part of Windows) failed to
  compile real Cycles kernels and was tens of times slower where it succeeded
  (measurements: `third_party/dxc-import.json`). The pinned, unchanged,
  Microsoft-signed `dxcompiler.dll` 1.9.2609.5 (University of Illinois/NCSA
  license) is a reviewed payload file in `native/binaries/<rid>/runtime/` beside
  its license text; it ships beside the host library, where the device finds it
  (`CODEBRIX_CYCLES_DXC_PATH` overrides the location). `dxil.dll` is not needed
  (DXC 1.8.2505 and later validate internally) and is not imported.
- **clang-cl from Visual Studio.** The toolchain is Visual Studio 2022 or later
  with its MSVC tools, Windows SDK and bundled LLVM (clang-cl, lld-link,
  llvm-lib), and Visual Studio's own CMake and Ninja
  (`tools/windows_toolchain.py`). It produces MSVC-ABI DLLs, accepts Clang's
  arithmetic options (the fixed-baseline CPU oracle) and is a Clang for the AST
  translation. Every other compiler distribution (Strawberry Perl, LLVM-MinGW,
  MSYS2, Cygwin, Git's Unix tools) is removed from the build environment and
  rejected in configured caches, compile commands and the compiler's dependency
  log, as the macOS recipes do for Homebrew.
- **Hybrid C runtime; no redistributable.** Every DLL links the C++ runtime
  statically and the Universal CRT (`ucrtbase.dll`, part of Windows 10 and 11)
  dynamically (`/MT` with `/NODEFAULTLIB:libucrt.lib ucrt.lib`), as .NET's own
  runtime does. No Visual C++ Redistributable is needed, and all DLLs share the
  Universal CRT's heap, so memory crosses DLL boundaries safely. The recipes
  reject any DLL that imports a Visual C++ runtime DLL.
- **Fixed-baseline CPU oracle.** As on Linux and macOS: Cycles' SSE4.2 kernels
  only on x64 (no AVX2/FMA kernel, never a native-architecture flag), the ARMv8-A
  base level on ARM64, no floating-point contraction and no reciprocal math.
  clang-cl ignores GCC-style math options with only a warning, and Cycles passes
  its own as `/clang:-ffp-contract=on /clang:-freciprocal-math`; the shared
  injection (`native/tools/inject_cycles.cmake`) and `native/host/targets.cmake`
  switch them off again in the same `/clang:` form, and the recipe checks the
  CPU kernel's compile line (last contraction and reciprocal options off, static
  runtime, SSE4.2 and no AVX/FMA on x64).
- **No image files.** As on macOS: OIIO's format plugins are all disabled,
  libpng is not built, `CBC_HOST_NO_IMAGE_FILES` is set, and the host rejects
  texture `filename` sockets with `CBC_UNSUPPORTED`. Callers pass decoded pixels;
  read and write image files with CodeBrix.Imaging, which the package does not
  depend on.
- **The same kernels as Linux.** The WGSL overlay is generated by the shared
  generators; on Windows the AST translation runs clang++ from Visual Studio.
  The generated `translated.wgsl` is byte-identical to the Linux copies retained
  in `native/evidence/*/generated/translated.wgsl`. Generated files are written
  with `\n` line endings (the recipe makes `Path.write_text` keep them), so the
  overlay bytes match Linux.
- **The pinned sources are unchanged.** A few Windows-only build helpers that
  the reviewed source profile excludes are replaced by independent files in
  `tools/dependencies/windows/` (zstd's and expat's version resource scripts,
  robin-map's debugger visualizer), placed into the recipe's work copy of the
  snapshot and recorded in the prefix provenance. Boost's in-repository build
  adapter defines the `BOOST_<LIB>_SOURCE`, `BOOST_ALL_DYN_LINK` and
  `BOOST_ALL_NO_LIB` macros that Windows DLLs need (`if(WIN32)` only).
- Reviewed deliverables go to `native/binaries/<rid>/` (runtime, unstripped and
  symbols) with provenance. The maintainer makes every commit and push.

## Build

From the repository root, in PowerShell or a Command Prompt (Git Bash rewrites
`/flag` arguments into paths):

```
python -I -X utf8 tools/dependencies/build_windows.py --rid win-x64 --jobs 16
python -I -X utf8 native/tools/build_cycles_windows.py --rid win-x64 --jobs 16
python -I -X utf8 tools/dependencies/build_windows.py --rid win-arm64 --jobs 16
python -I -X utf8 native/tools/build_cycles_windows.py --rid win-arm64 --jobs 16
```

`python -I -X utf8` is required: the recipes read every text file as UTF-8, as
on Linux and macOS, and `-I` ignores `PYTHONUTF8`. Each recipe records its
inputs (`provenance.json`, `invocation.json`) and `status.json`.

## Process exit with live hosts

`ABI.md` promises that a process may exit while hosts are alive. On Windows a
DLL's own `atexit` functions run at `DLL_PROCESS_DETACH`, after `ExitProcess`
has terminated every other thread, so closing the hosts there crashed
(`0xC0000409`, found by the host gate's `cpu-exit` step). The host registers its
exit hook in the process-wide table instead (`_crt_atexit`, which `exit()` runs
while all threads exist) and pins its DLL so the hook can never outlive it
(`native/host/cycles_host.cpp`); Linux and macOS keep `std::atexit`.

## Diagnostics for driver problems

A device run on the Qualcomm Adreno 680 found GPU-driver problems that the
binaries could not narrow without a rebuild per experiment
([docs/TESTING-WINDOWS-ARM64.md](../../docs/TESTING-WINDOWS-ARM64.md), F1, F3,
F4). The host therefore has opt-in diagnostics, all environment variables, all
off by default. They are implemented in the shared device code and work on every
WebGPU RID. Each one that is set is printed once to stderr ("CodeBrix Cycles
diagnostic active (not a validation run)") and listed in the device report
(`deviceReport.webgpu.diagnostics`, `diagnostic: true`). `windows_host_gate.py`
records them and never passes while any is active (or while the adapter is
layered, see Dozen below), so the stager can never stage a diagnostic run;
`render_oracles.py` records them in `run.json` (`diagnosticRun`).

| Variable | Effect |
|---|---|
| `CODEBRIX_CYCLES_WGSL_LOAD=DIR` | Compile edited WGSL in place of the generated (specialized, tier-adjusted) source. One module name is compiled in several variants (entry sets, features, tiers), so each variant is keyed `<module>-<hash>`, the hash being the first 16 hex digits of the SHA-256 of the WGSL that would be compiled. A variant without an override writes `DIR/<key>.generated.wgsl` once; copying that file to `DIR/<key>.wgsl` and editing it makes exactly that variant compile the edited text. Workflow: run once with an empty `DIR`, copy and edit the module of interest, run again, compare with the CPU film. The loaded file's SHA-256 is listed. |
| `CODEBRIX_CYCLES_WEBGPU_ADAPTER=hardware\|software\|<name>` | `hardware` is the default rule (the first integrated or discrete adapter; on Apple builds an Intel adapter first, so Intel + AMD Macs use the Intel GPU). `software` picks a CPU adapter: WARP on Direct3D 12 (part of Windows), llvmpipe on Vulkan. That is a full-kernel reference on the same machine, same WGSL and same DXC, which separates "our code is wrong" from "this driver is wrong" in one render; but WARP is very slow with these kernels (on a current x64 laptop it had not finished creating the first module's pipelines after 5 minutes, and the example scene ran for more than 2 hours), so use it only on a tiny scene (one pixel or a few, one sample) or leave it for an overnight run. Anything else selects the first adapter whose device name or description contains it (case-insensitive). The device report lists every enumerated adapter (`deviceReport.webgpu.adapters`). |
| `CODEBRIX_CYCLES_WEBGPU_ALLOW_NONCOMPLIANT=1` | Sets `WGPUInstanceFlag_AllowUnderlyingNoncompliantAdapter`. With `CODEBRIX_CYCLES_WEBGPU_BACKEND=vulkan` this exposes Mesa's Dozen (Vulkan on Direct3D 12) on Windows on ARM devices that have no native Vulkan driver. A Dozen adapter is reported with `layeredOn` "Direct3D 12 (Mesa Dozen)": it compiles SPIR-V to DXIL with Mesa's compiler and runs on the same D3D12 driver, so it is a diagnostic and never Vulkan evidence. |
| `CODEBRIX_CYCLES_DXC_MAX_SHADER_MODEL=6.0`...`6.7` | Caps the shader model DXC targets (default 6.7). A lower model changes the DXIL a driver compiles; a cheap first experiment against a driver compiler bug. Direct3D 12 only. |
| `CODEBRIX_CYCLES_WEBGPU_INSTANCE_FLAGS=debug,validation,gpu-based-validation,discard-hal-labels,with-env` | wgpu instance flags. `validation` enables the D3D12 debug layer (or the Vulkan validation layers), `gpu-based-validation` D3D12 GPU-based validation; both need the Windows "Graphics Tools" optional feature. `with-env` lets wgpu read its own `WGPU_*` variables. The layers' messages arrive only through wgpu's log, so combine this with `CODEBRIX_CYCLES_WEBGPU_LOG`. |
| `CODEBRIX_CYCLES_DRIVER_WORKAROUNDS=none` | Turns off every driver workaround (see "Driver workarounds" below), to check whether a new driver still needs one. |
| `CODEBRIX_CYCLES_WEBGPU_LOG=error\|warn\|info\|debug\|trace` | Prints wgpu's log on stderr (`wgpu <level>: ...`). `warn` shows which stage failed and how (for example "Shader translation error ... (0x80070057)", which wgpu reports for a failed `CreateComputePipelineState`; a DXC failure reads "DXC compile error"). `debug` also prints the HLSL naga generated for every pipeline ("Naga generated shader for ..."), which `dxc.exe -T cs_6_7 -E <entry> -HV 2018` compiles offline; the output is large (12 MB for one light-tree scene). |
| `CODEBRIX_CYCLES_DEBUG_OUTPUT=shading-normal\|geometric-normal\|svm-normal\|uv\|flags` | The first camera hit writes one `SurfaceData` field to the Combined film instead of radiance, raw, and the path ends there: the interpolated shading normal before shader evaluation, the geometric normal, the shading normal after shader evaluation (bump, normal map), (u, v, primitive) or (shader, object, runtime flags). A non-finite component is written as 1e30. Compare the GPU film with the same mode on `software` (WARP) or with the CPU's expectation. The code is a `DEBUG_OUTPUT` region of `wavefront_surface.wgsl` (feature bit 116, outside `SF_ALL`), so every module is byte-identical to a build without it unless the variable is set. |

### Driver workarounds

A driver workaround is product behavior, not a diagnostic: it is keyed to the
adapter, on by default where it applies, leaves the images unchanged, and is
listed in the device report (`deviceReport.webgpu.driverWorkarounds`).
`CODEBRIX_CYCLES_DRIVER_WORKAROUNDS=none` turns every workaround off (a
diagnostic, listed like the others above) to check whether a new driver still
needs it.

| Name | Applies to | What it does |
|---|---|---|
| `intel-d3d12-shader-cache` | Intel adapters (vendor 0x8086) on Direct3D 12 | The driver's cached compile of a pipeline that walks the light tree is broken, while its first compile is correct ([TESTING-WINDOWS-X64.md](../../docs/TESTING-WINDOWS-X64.md), W1). The `DRIVER_CACHE_SALT` region of `wavefront_light_tree.wgsl` (feature bit 117, outside `SF_ALL`) compares the walk's receiver with a constant no object index reaches (0xF0000000 to 0xFFFFFFFE), which the host makes different for every compile. Those pipelines therefore never come from the driver's cache; every other pipeline compiles byte-identically. Cost: those pipelines compile cold in every process. |
| `intel-metal-surface-workgroup` | Intel adapters on Metal (osx-x64; matched by device name, since Metal reports no vendor ID) | The Intel Metal compiler computes wrong, non-repeatable values in `prepare_surface` and `prepare_surface_raytrace` whenever a workgroup holds more than one invocation (motion-blur and AO-node scenes; [TESTING-MACOS-X64.md](../../docs/TESTING-MACOS-X64.md), M2). Those two entry points are compiled with `@workgroup_size(1)`; dispatch reads the declared size, every other entry point compiles unchanged, and the images are those of the CPU kernels. Cost on a UHD 630: about 1-7% of render time. |

A correctness canary is not built into scene creation (on the Adreno one surface
pipeline takes 30 to 90 s to compile). The host gate's driver-coverage step is
the canary instead: it renders one oracle scene per failure class found so far
(smooth shading `linux-gates/glass-render`, motion blur with a normal map
`linux-gates/deforming-motion-1`, glass lit by an area light
`starter/glass-and-area-light`, and the light tree, which is on by default,
`light-tree/lamps-and-mesh-lights`) on the CPU and the GPU and requires the
practical criterion.

`render_oracles.py --payload native/binaries/<rid>` renders the corpus from a
staged payload: it verifies the payload against its `provenance.json`, assembles
`<output>-payload-run` from it and the pinned WebGPU runtime (as
`windows_host_gate.py --payload` does) and runs the payload's oracle runner.
